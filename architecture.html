◈ Spendly

How the expense tracker is put together

A single-process Flask monolith: server-rendered Jinja2 templates, session-cookie auth, and hand-written SQL against a local SQLite file. No ORM, no blueprints, no build step.

Flask 3.1.3 Werkzeug 3.1.6 SQLite 3 Jinja2 pytest 8.3.5 branch: main

System map

Every request is served by one Python process. The only persistent state lives in a SQLite file next to the code; everything else — who you are, what page you are on — rides in a signed cookie or dies with the request.

Request lifecycle

What happens between a form submit and the next page, in order.

01
Flask matches the URL to a view in app.py
All ten routes are declared at module level — there is no app factory and no blueprint registry.
02
@login_required checks the session
If user_id is absent from the signed cookie, the visitor is redirected to /login. Only /dashboard and /expenses/add carry the decorator today.
03
db.get_db() hands back the request’s connection
Opened once and cached on flask.g, so repeated calls in one request reuse it. Foreign keys are re-enabled per connection, because SQLite forgets that setting every time.
04
The view validates input and runs SQL inline
Validation is plain Python in the handler; queries are parameterised strings. There is no model or service layer between the route and the database.
05
render_template() builds the response
The inject_current_user context processor supplies current_user to every template, so base.html can swap the nav between signed-in and signed-out.
06
teardown_appcontext closes the connection
Registered by db.init_app(app). Nothing is pooled and nothing survives the request except the cookie.

Data model

Two tables, created by init_db() with CREATE TABLE IF NOT EXISTS. Bootstrap and seed with python -m database.db.

users

2 seeded
  • idINTEGER pk autoincrement
  • nameTEXT not null
  • emailTEXT not null unique
  • password_hashTEXT not null
  • created_atTEXT default datetime('now')
hashed with werkzeug · email lower-cased at the route

expenses

10 seeded
  • idINTEGER pk autoincrement
  • user_idINTEGER fk → users.id
  • amountREAL check ≥ 0
  • categoryTEXT not null
  • descriptionTEXT nullable
  • spent_onTEXT not null
  • created_atTEXT default datetime('now')
ON DELETE CASCADE · idx_expenses_user_id

seed_db() is safe to re-run: users go in with INSERT OR IGNORE on the unique email, and each seed expense is skipped if a matching row already exists for that user. Categories are a hard-coded list in app.py, not a table.

Known gaps

Things the diagram implies but does not spell out, worst first.

account takeover /reset-password verifies nothing
The handler takes an email and a new password and writes the new hash straight to that account. There is no emailed token, no current-password check and no signed-in requirement, so anyone who knows a registered address can take the account. This should be gated before anything else ships on top of it.
before implementing The stub routes are unguarded
/profile, /expenses/<id>/edit and /expenses/<id>/delete have no @login_required. Edit and delete also need to scope by user_id in the WHERE clause, or any signed-in user will be able to touch another user’s rows by guessing an id. Delete should be a POST as well — a GET that destroys data can be fired by a prefetch or an image tag.
no csrf Every form posts without a token
Session auth plus cookie-only identification means a third-party page can submit these forms on a signed-in user’s behalf. Flask-WTF or a hand-rolled token in base.html would close it.
structural No app factory, no migrations
app is built at import time and DB_PATH is a module constant, so tests have to monkeypatch the path rather than configure it. The schema only ever runs CREATE TABLE IF NOT EXISTS, which will not alter a table that already exists — the first column change will need a real migration story.
deployment Development configuration only
The Werkzeug dev server runs with debug=True, and SECRET_KEY falls back to "dev-secret-change-me" when the environment variable is missing — which would let anyone forge a session cookie in production.
